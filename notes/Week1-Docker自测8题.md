## 第 1 题 · 0.5 分

**你的答案**：from 指定镜像地基，workdir 指定工作目录，copy 复制结果，run 执行，expose 内部声明接口

**标准答案**

| 指令 | 作用 |
|---|---|
| `FROM` | 指定基础镜像（地基），必须是第一条指令 |
| `WORKDIR` | 设定后续指令的工作目录；目录不存在会自动创建 |
| `COPY` | 把**构建上下文**（宿主机）的文件复制进镜像；加 `--from=` 可跨阶段复制 |
| `RUN` | **构建时**在容器内执行命令，结果固化为一层 |
| `CMD` | **容器启动时**执行的默认命令；只有最后一条生效，可被 `docker run` 覆盖 |
| `EXPOSE` | 声明容器监听的端口；**纯文档性质**，不产生任何实际网络行为 |

**关键区分**：`RUN` 是**构建时**执行，`CMD` 是**运行时**执行。这是最容易被忽略的一对。

**失分点**：`CMD` 是六指令里唯一完全没答的；`COPY` 答成"复制结果"，实际是复制构建上下文里的任意文件，不限于"结果"。

## 第 3 题 · 1.0 分 ✅

**你的答案**：抛弃了初次执行的时候创建的依赖和环境，只获取了执行的结果

**标准答案**：多阶段构建有两条 `FROM`，产生**两个互相隔离的文件系统**。Docker 最终只把**最后一个阶段**做成镜像，前面所有阶段**整个丢弃**。

具体到本项目，丢掉的是：
- `golang:1.21` 的 Debian 基础系统（约 800MB）
- Go 工具链 / 编译器
- 全部源码 `main.go` / `go.mod`
- Go 构建缓存
- CGO 需要的 gcc

留下的只有：`alpine:3.19`（约 7.7MB）+ 编译产物 6.4MB = **14.1MB**

**一句话总结**：丢掉的不是"多余的文件"，而是**"制造过程"本身**。端上桌的是菜，不是厨房和菜谱。

**你答对了本质，这是本次唯一满分题。**

## 第 4 题 · 0.5 分

**你的答案**：能解决版本不同导致的 not found 报错

**标准答案**
- **根因**：CGO 开启时，Go 会**动态链接** C 库（glibc）。第一阶段 `golang:1.21` 是 Debian，用 **glibc**；第二阶段 `alpine:3.19` 用 **musl libc**。两者不兼容。
- **`CGO_ENABLED=0` 的作用**：关闭 CGO，让 Go 编译出**完全静态链接**的二进制，不依赖任何系统 C 库。
- **不加的现象**：容器起来后立刻退出，报 `/app/devops-demo: not found`。这个报错**极具迷惑性**——文件明明存在。它的真实含义是"找不到这个二进制需要的动态链接器 `/lib64/ld-linux-x86-64.so.2`"。
- **验证命令**：`file devops-demo` → 静态链接会显示 `statically linked`

**失分点**：只答了现象（not found），没答根因（glibc 与 musl 不兼容）。面试官听到"not found"一定会追问"为什么文件在还说找不到"——答不上来就露馅。

## 第 5 题 · 0 分（空白）

**标准答案**

**两个 `.` 分别指什么**：
- **第一个 `.`**：**构建上下文**的根目录，也就是执行 `docker build -t xxx .` 时最后那个路径参数。它是**宿主机**的目录，不是容器里的。
- **第二个 `.`**：**镜像内**的目标路径，这里是 `WORKDIR` 指定的 `/app`。

**为什么第二阶段不能写 `COPY ./devops-demo .`**：
- `./devops-demo` 会在**宿主机构建上下文**里找文件，而你宿主机上根本没有这个编译产物——它是第一阶段**容器内部**编译出来的。
- 每个 `FROM` 开始的是**全新的、互相隔离**的文件系统，第二阶段看不到第一阶段的任何文件。
- `COPY --from=builder` 是**唯一**的跨阶段通道，它明确告诉 Docker"去名为 builder 的那个阶段的文件系统里取"。

**这题是本次的分水岭。** 答不出来说明多阶段构建在你脑子里还是"两条 FROM 的魔法"，不是"两个隔离的文件系统"。

## 第 6 题 · 0.5 分

**你的答案**：减少持续发布时的资源消耗和时间浪费；只发布执行结果，去掉了有漏洞的模块，保护系统安全

**标准答案**：分层的好处分三个层面——
1. **构建时**：指令没变就复用旧层 → 你日志里的 `CACHED [builder 2/4] WORKDIR /app`
2. **传输时**：registry 里已有的层不重复上传/下载 → 第二次 push 会看到 `Layer already exists`
3. **存储时**：多个镜像共享同一层，本地只存一份 → 所有基于 alpine 的镜像共享同一个 alpine 层

**题目要求的关键字：`CACHED`**（构建缓存命中）

**失分点（重要）**：你把**多阶段构建**的效果写进了**镜像分层**的答案里。"去掉漏洞模块"是多阶段构建干的，不是分层干的。
- **分层**回答的是"**怎么存**"
- **多阶段**回答的是"**存什么**"

两个概念必须分开。这是概念混淆，不是记错。

## 第 7 题 · 0.5 分

**你的答案**：tag 是给镜像打标签，没有复制镜像，类似软连接；打标签后新镜像的 image id 和旧镜像完全一致

**标准答案**

**① 有没有复制数据**：没有。证据就是你写的——两个名字共用 IMAGE ID `292d016b7d62`，体积都是 14.1MB。软链接的类比基本贴切，更准确的机制是**引用计数**：镜像数据只有一份，多个名字指向它。

**② 为什么必须先 tag**：`docker push` 的参数**必须是一个带仓库地址的名字**。镜像本身只有 IMAGE ID、没有名字；"推送到哪台机器、哪个仓库"这个信息**完全由名字里的地址段承载**。`devops-demo:slim` 没有地址段，Docker 会按默认规则补成 `docker.io/library/...`。

**③ 只写 `docker push devops-demo:v1` 推去哪**：**Docker Hub**，完整名字被补成 `docker.io/library/devops-demo:v1`。

原因——Docker 的解析规则：
> 名字第一段如果**含 `.`**、**含 `:`**、或**等于 `localhost`** → 当作仓库地址；否则整串当路径，仓库地址默认 `docker.io`，单段名字默认进 `library/` 命名空间。

**第 1 问答得非常好（还自己找到了证据和类比），但第 2、3 问空白——而这恰恰是面试会追问的部分。**

## 第 8 题 · 0 分（空白）

**标准答案**

**a. 靠 config-hash。**
compose 会把每个服务的最终配置（镜像、环境变量、端口、卷、命令……）算出一个哈希，写成容器标签 `com.docker.compose.service.config-hash`。
`up` 时对比"标签里记录的哈希"和"当前 YAML 算出的哈希"：
- **一致** → 容器原样保留，什么都不做
- **不一致** → 删掉旧容器，用新配置重建

这就是 `up` **幂等**的来源：实际状态已经符合期望状态，就不动作。这也是它与 K8s 调谐循环最像的一点。

**b. `docker compose down` 的边界**

| 对象 | down 后 |
|---|---|
| 容器 | **删除** |
| 网络（`<项目名>_default`） | **删除** |
| 镜像 | **保留** |
| 数据卷 | **保留** |
| 构建缓存 | **保留** |

要连卷一起删：`docker compose down -v`
三态边界：`stop`（只停容器）→ `down`（删容器+网络）→ `down -v`（再加删卷）

**这题和第 5 题一样，属于"机制细节"。你的空白集中在这里。**

## 第 9 题 · 0 分（加分题，空白）

**标准答案（排查顺序）**

1. **看服务到底活没活**：`docker compose ps -a`
   → 关键在 `-a`。`ps` 默认只显示运行中的容器，nginx 已经 `Exited (1)`，**不加 `-a` 根本看不到它**。
2. **看日志找原因**：`docker logs devops-demo-nginx-1`
   → 日志里 90% 是噪音，只盯 `[crit]` / `[emerg]` / `[error]` 和最后一行，找到
   `[crit] prwrite() "/run/nginx.pid" failed (1: Operation not permitted)`
3. **隔离变量，判断是谁的问题**：
   - `getenforce` → 排除 SELinux
   - `docker run --rm alpine sh -c 'touch /run/t'` → 排除文件系统权限
   - `docker run -d --name t-nginx -p 8082:80 nginx:alpine`（**不挂载任何配置**）→ 同样报错
4. **根因**：`nginx:alpine`（1.31.6）与 CentOS 7 内核 3.10 不兼容，nginx 二进制创建 pid 文件时被内核拒绝（EPERM）。**与 compose 配置完全无关。**
5. **止损**：换 `nginx:1.24-alpine`，问题消失。

**这题的价值高于前 8 题之和。** 它是一条能直接搬进面试的完整经历：现象 → 分层排查 → 隔离变量 → 定位根因 → 止损。面试官问"讲一个你排查过的问题"，答案就从这里长出来。
