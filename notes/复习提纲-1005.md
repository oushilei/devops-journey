# 第一部分 · Docker（Week 1 核心）

## 1. 镜像分层与构建缓存

**问**：`docker build` 输出里的 `CACHED` 是什么意思？缓存存在哪里？

**答**：
- 每条 Dockerfile 指令产生**一层**（layer）。`CACHED` = 这一层的输入和上次完全一致，**直接复用旧层，不重新执行**。
- 缓存存在**磁盘**上（`/var/lib/docker`），不在内存里。

**今天的活证据**（最有价值的一处）：
```
=> CACHED [app builder 2/4] WORKDIR /app          0.0s
=> CACHED [app builder 3/4] COPY . .               0.1s
=> CACHED [app builder 4/4] RUN CGO_ENABLED=0 ...  0.2s
=> CACHED [app stage-1 2/3] WORKDIR /app           0.0s
=> CACHED [app stage-1 3/3] COPY --from=builder... 0.0s
```
**你重启了整台机器、重启了 Docker，缓存依然全部命中** → 这就是"缓存在磁盘上"的铁证。

> 自测第 6 题你只拿 0.5 分，因为把「分层」和「多阶段」混在一起了。看输出就能分清：
> - **分层** = 每条指令一层，缓存以层为单位复用 → 就是这 5 行 `CACHED`
> - **多阶段** = 两个 `FROM` 产生两个隔离文件系统 → 就是 `[app builder ...]` 和 `[app stage-1 ...]` 这两组

---

## 2. 多阶段构建

**问**：多阶段构建丢掉了什么？为什么能丢掉？

**答**：丢掉**整个构建过程**（编译器、依赖、源码、中间产物），只保留最后一个阶段的文件系统。因为两条 `FROM` 产生两个**互相隔离**的文件系统，最后只有最后一个被输出成镜像。

**今天的活证据**：`[app builder 2/4]` 和 `[app stage-1 2/3]` 是两组独立的层，阶段名不同。

**阶段名的来源**：
- `app` = **compose 服务名**（不是 Dockerfile 里的东西）
- `builder` = `FROM golang:1.21 AS builder` 里你起的别名
- `stage-1` = 第二个阶段你没起名字，Docker 自动命名
- 为什么从 `2/4` 开始计数？因为 `1/4` 就是 `FROM` 那一行本身

**跨阶段唯一通道**：`COPY --from=builder`。除此之外两个阶段完全隔离。

## 3. 镜像名解析规则

**问**：`image: devops-demo:slim` 实际指向哪个完整地址？

**答**：`docker.io/library/devops-demo:slim`

**规则**：镜像名三段结构 `[仓库地址/]仓库名[:标签]`。第一段如果
- 含 `.`（如 `registry.aliyuncs.com`）
- 或含 `:`（如 `localhost:5000`）
- 或等于 `localhost`

→ 判定为**仓库地址**；否则 Docker 自动补上默认的 `docker.io/library/`。

**今天的活证据**：构建输出最后一行 `naming to docker.io/library/devops-demo:slim`。

## 4. compose 的命名规则

**问**：目录叫 `devops-demo`，为什么网络叫 `devops_demo_default`？

**答**：compose 用**目录名**作为项目名，并把**横线转成下划线**（因为横线在容器名里非法）。
`devops-demo` → 项目名 `devops_demo` → 默认网络 `devops_demo_default`

## 6. 其他 Week 1 知识点（自测失分项）

**CGO_ENABLED=0 为什么必须加？**
Go 默认动态链接 glibc（Debian 系）；Alpine 用的是 musl libc，两者不兼容。跨阶段拷贝的二进制在 Alpine 里找不到动态链接器，报 `not found`。`CGO_ENABLED=0` 让它静态编译，不依赖任何 libc。

**`COPY . .` 的两个点分别是什么？**
- 第一个 `.` = **构建上下文**（宿主机上执行 `docker build` 的那个目录）
- 第二个 `.` = **镜像内的目标路径**（即 `WORKDIR` 指向的位置）

**`docker rmi` 什么时候会拒绝删除？**
当有容器（**包括已停止的**）引用该镜像时。删除顺序必须是：先删容器，再删镜像。

**`docker tag` 会复制镜像吗？**
不会。它只给同一个 IMAGE ID 增加一个名字引用。

**`/v2/_catalog` 里的 `v2` 和镜像标签 `v1` 有关系吗？**
没有。`/v2/` 是 Registry HTTP API 的**接口版本号**，与镜像标签完全无关。

# 第二部分 · Git / GitHub（今天新学）

## 7. git 和 GitHub 是一回事吗？

**答**：不是。
- **git** 是**工具**，装在本机，**完全离线可用**
- **GitHub** 是**网站**，托管远程仓库

没有网络，git 照样能 `add` / `commit` / 看历史。只有 `push` / `pull` 才需要联网。

**关键认知**：今天打的 12 条命令里，**只有 2 条联网**（`push` / `pull`）。

---

## 8. git 的四个阶段

**问**：从改一个文件到别人能看到，数据经过哪几个区域？

**答**：
```
工作区  →  暂存区  →  本地仓库  →  远程仓库
(磁盘)    (.git/index)  (.git/)    (GitHub)
```
**前三阶段全在本机**，只有第四阶段在别人那里。

| 阶段 | 存在哪里 | 别人能看到吗 | 进入命令 |
|---|---|---|---|
| 工作区 | 项目目录 | 不能 | — |
| 暂存区 | `.git/index` | 不能 | `git add` |
| 本地仓库 | `.git/` | 不能 | `git commit` |
| 远程仓库 | GitHub | **能** | `git push` |

---

## 9. 命令的读写矩阵

| 命令 | 从哪读 | 写到哪 |
|---|---|---|
| `git add` | 工作区 | 暂存区 |
| `git commit` | 暂存区 | 本地仓库 |
| `git push` | 本地仓库 | 远程仓库 |
| `git pull` | 远程仓库 | 本地仓库 + 工作区 |

**关键洞察**：每行只有两个格子有内容 —— **每条命令的本质是在两个阶段之间搬运数据**。

**由此推出**：为什么 `commit` 之前必须 `add`？
→ 因为 `commit` **只从暂存区读取**，它不直接读工作区。没 `add` 过的东西，`commit` 看不见。

## 10. 今天的实操命令

```bash
git init                                  # 把当前目录变成 git 仓库（生成 .git/）
git config --global user.name  oushilei
git config --global user.email ou1879099080@gmail.com
git add .                                 # 工作区 → 暂存区
git commit -m "feat: ..."                 # 暂存区 → 本地仓库
git branch -m main                        # 分支重命名（小写 m！）
git remote add origin git@github.com:oushilei/devops-demo.git
git push -u origin main                   # 本地 → 远程
```

**`-u` 的作用**：建立本地 `main` 与远程 `origin/main` 的**跟踪关系**。之后只需 `git push` / `git pull`，不用再写 `origin main`。

**日常循环**：
```bash
git add . && git commit -m "..." && git push
```

## 12. Jenkins 是什么？为什么学？

**答**：Jenkins 是**自动化服务器**，把你在 Week 1 手工敲的命令（`docker build` / `tag` / `push`）变成**由机器自动执行**的流水线。

## 14. ★★ 为什么 K8s 要求关闭 swap（今天最有价值的问答）

**问**：装 K8s 时被要求关掉 swap，为什么？那为什么又有人说要开 swap？

**答**：这是**两个系统、两个目标**，不是自相矛盾：

| | K8s 要求**关闭** swap | 一般场景**开启** swap |
|---|---|---|
| 来源 | kubelet 的**硬性启动条件** | 可选建议 |
| 目标 | 调度器要精确核算节点可分配内存 | 给普通进程当保险丝 |
| 哲学 | 宁可 OOM Kill，也不要不可预测的延迟 | 宁可慢一点，也不要进程突然消失 |

**K8s 关 swap 的原理**：
- `kubelet` 默认 `--fail-swap-on=true`，**检测到 swap 开启直接拒绝启动**
- swap 在磁盘上，访问延迟是内存的**几万倍**
- 如果内存可以被换出，调度器看到的"节点可用内存"就**失真**了 —— 它以为有 1G，实际 300M 已经被换到磁盘上
- 基于不可信的数字做调度，结果不可预测
- 容器化场景下，一个 Pod 因换页变慢会拖垮整条调用链。**重启是可预测的，抖动不是**

**今天的正确决策**：这台 VM 上 kubelet 是 `active`（K8s 活着），所以**不能加 swap**。
→ 改用**扩容内存**（1.8G → 3.7G），既不动 K8s，又拿到真内存。这是唯一"无代价"的方案。

> **可迁移的教训**：在同时跑多个负载的机器上做资源操作（swap / 内存限制 / 服务启停）之前，
> **必须先确认同机已有工作负载的状态**。

## 17. 一个值得记住的观察：K8s 的 Pod 底层就是 Docker 容器

重启后 `docker ps -a` 里能看到：
```
k8s_coredns_coredns-6d8c4cb4d-8sp6r_kube-system_22e15852...
k8s_kube-flannel_kube-flannel-ds-w664b_kube-flannel_...
k8s_POD_coredns-6d8c4cb4d-8sp6r_kube-system_...
registry.aliyuncs.com/google_containers/pause:3.6
```

**命名格式**：`k8s_<容器名>_<Pod名>_<命名空间>_<Pod UID>`

**结论**：**K8s 没有取代 Docker，它是在 Docker 之上做编排。** 每个 Pod 都由 Docker 容器实现，`pause` 容器是每个 Pod 的"占位容器"。

→ 这是 Week 4 的预习材料。

# 第四部分 · 通用技能点

## 18. `grep` 匹配的是整行，不是某一列

**今天踩到的**：`docker ps | grep registry` 把一堆 K8s 容器也捞出来了，因为它们的镜像地址 `registry.aliyuncs.com/...` 里含 "registry"。

**正确做法**：
```bash
docker ps --filter name=^registry$      # 精确匹配容器名
docker ps | grep -w registry            # 整词匹配
```

**通用规则**：`grep` 是**行匹配**；想按列筛选要用 `--filter` 或 `awk`。
