## 表述 A · 镜像优化

### 你的初稿

> 这一块我主要是做了 go 服务容器化并部署；最开始创建的容器大约占了 884mb 的存储空间，之后我错了多阶段构建，用了两条 from，只把第一阶段的编译结果制作成镜像，多阶段构建出来的镜像只有 14mb，大概缩小了 62 倍。之所以能缩小这么多是因为我第二次构建的时候舍弃了整个服务的"生产过程"，最终只保留了最后的结果。这个成果在真实环境中意味着更短的拉去时间，更小的存储空间，更小的攻击面，完美符合奥卡姆剃刀原理。

### 批改

**结论：结构 6 点全部命中，这是明显的进步。但深度不足，且结尾有一处明显败笔。**

#### ✅ 做对的三点

1. **结构完整**——背景 / 起点数字 / 动作 / 结果 / 原理 / 价值，六个位置都有内容，没有漏
2. **有数字**——884MB、14MB、62 倍，不是空话
3. **原理抓得准**——"舍弃了整个服务的生产过程，最终只保留了最后的结果"，这句话是对的，而且表达得比标准答案更形象

#### ❌ 问题一（最严重）：结尾的"奥卡姆剃刀原理"

**这句话是负分项，必须删掉。** 三个理由：

1. **强行拔高**。奥卡姆剃刀是"如无必要勿增实体"的哲学原则，跟镜像分层没有直接关系。评审方的第一反应是"这人在掉书袋"。
2. **替代了本该有的技术结论**。结尾是整个表述最值钱的位置，应该放一个能落地的技术判断，而不是一个哲学名词。
3. **它是个坑**。评审方只要追问一句"你说的奥卡姆剃刀具体指什么"，你就答不上来了。

> **黄金法则：每个名词都要能承受追问。承受不住的名词，就是给自己挖坑。**

正确做法：把结尾换成**量化的工程后果**（见下）。

#### ❌ 问题二：价值只有定性，没有定量

你写的"更短的拉取时间、更小的存储空间、更小的攻击面"——**任何没做过这件事的人也说得出来**。

技术要点的杀伤力全部来自数字。加上这一步：

```
按 20 个节点的集群算：
  优化前：884MB × 20 = 17,680MB ≈ 17.3GB
  优化后：14.1MB × 20 = 282MB
  一次全量分发的总下载量降到原来的 1.6%
```

同一句话，有算式和没算式，评审方对你的判断完全不同。

#### ❌ 问题三：缺"第二阶段的构成"

你说"用了两条 FROM"，评审方一定会追问：**"那第二阶段里到底装了什么？"**

必须能答出：
```
第二阶段 = alpine:3.19（约 7.7MB）+ 编译产物 devops-demo（6.4MB）= 14.1MB
```

这个数字你在实验里验证过：`docker exec demo-slim ls -la /app` 只有**一个文件，6,722,897 字节**。

#### ❌ 问题四：缺"如何验证优化没把功能搞坏"

评审方会想：你把东西砍了 98%，怎么保证程序还能跑？

你有现成的答案，但没写进去：
- `curl localhost:8080` 返回的 `host:` 是**容器 ID**，与 `docker ps` 里的 ID 前 12 位一致
- `docker exec demo-slim ls -la /app` → 只有 1 个文件

**"我怎么确认我的优化没把功能搞坏"——这一句体现的是工程成熟度，比体积数字本身更能加分。**

### 参考版（**不许照抄**，看完自己重写一遍）

> 我这一周做的是把一个 Go 写的 HTTP 服务容器化。一开始用的是最直接的做法——基础镜像直接用 golang:1.21，把源码拷进去、编译、跑起来。这样打出来的镜像 884MB。
>
> 884MB 的问题在于，它把整个**编译环境**都装进了交付物里：Debian 系统、Go 工具链、gcc、源码、还有构建缓存——这些在运行时一个都不需要。
>
> 所以我改成多阶段构建，用两条 FROM。第一阶段还是 golang:1.21，负责编译；第二阶段换成 alpine:3.19，只把第一阶段编译出来的那个二进制文件拷过来。最终镜像 14.1MB，缩小了 62.7 倍。
>
> 具体构成是：第二阶段里只有 alpine 的 7.7MB 加上 6.4MB 的二进制，第一阶段整个被丢弃。
>
> 为了确认优化没把功能搞坏，我用 curl 访问服务，返回的 host 是容器 ID，和 docker ps 里的 ID 前 12 位对得上；再 docker exec 进容器看 /app 目录，里面只有一个文件。功能和体积两头都验证过。
>
> 这个数字在真实环境里的意义是：按 20 个节点的集群算，一次全量分发的总下载量从 17.3GB 降到 282MB；存储占用同样降下来；而且 884MB 里那套编译工具链和系统库本来就是漏洞扫描的重点，砍掉之后攻击面小了一大截。
>
> 后面我会把它推到镜像仓库，让 CI 流水线自动构建和分发。

**注意这版和你的初稿差在哪**：不是语言变漂亮了，而是**多了三类信息**——第二阶段的构成、验证方法、量化后果。这三样才是评审方真正想听的。

### 定稿（第 2 版 · 用户重写 + 4 处修正）

> 我主要做的是把一个 Go 写的 HTTP 服务容器化。一开始用的是最常规的方式：基础镜像直接用 golang，把整个源码拷进去、编译、跑起来，产出的镜像体积 884MB。
>
> 884MB 的问题在于，整个编译环境都被装进了交付物里——Debian 系统、gcc、源码、Go 工具链。这些东西在运行时一个都不需要。
>
> 所以我改成多阶段构建，用两条 FROM。第一阶段还是 golang，负责编译；第二阶段用 alpine，只把第一阶段编译出来的二进制文件拷过来。最终镜像里只有 7.7MB 的 alpine 和 6.4MB 的二进制，整个镜像 14.1MB，缩小了约 63 倍。
>
> **按一个 20 节点的集群来算**，这意味着一次全量分发的总下载量从约 17GB 降到 280MB，存储占用同样下降；而且 884MB 里那套编译工具链和系统库本身就是漏洞扫描的重点，砍掉之后攻击面也大幅下降。
>
> 至于优化的结果，我做了双重验证：功能层面用 curl 访问服务，返回的 host 是容器 ID，和 docker ps 里的 ID 前 12 位一致；体积层面用 docker exec 进容器看 /app，里面只有一个文件。两头都确认过。

1. "占用内存 884MB" → "镜像体积 884MB"
2. "在**一个有二十个节点的真实生产环境集群里**" → "**按一个 20 节点的集群来算**"

## 表述 B · nginx 与 CentOS 7 老内核不兼容

> **这是三段里最重要的一段**——它是唯一能直接回答评审方"讲一个你排查过的问题"的素材。
> 它的价值不在最后换了哪个 tag，而在**你能不能把责任范围一步步缩小**。

### 概念准备：什么是"隔离变量"

另一个名字是**控制变量法**。核心逻辑：

> 面对一个"起不来"的服务，**不要猜原因**，而是把可能的原因列全，
> 然后**每次用一个实验干掉一个**，直到只剩一个。

**每个实验必须预设结论**："如果是 A 结果，就说明是 X 的问题；如果是 B 结果，就说明不是。"
**没有预设结论的实验，做了等于没做。**

### 你在 Day2 实际做的三个隔离实验

| 实验 | 结果 | 排除了什么 |
|---|---|---|
| `getenforce` | Disabled | 排除 SELinux 拦截 |
| alpine 容器内写 `/run` 目录 | 成功 | 排除文件系统权限问题 |
| 起 nginx 但**不挂载自己的配置** | 报一模一样的错 | 排除自己的配置问题 |

三个实验做完，"四种可能"只剩一种：**镜像本身**。

### 表述全文

> 我用 docker compose 起了一个 app 加 nginx 反向代理的栈，compose 显示两个容器都 Started 了，但访问 8081 端口一直拒绝连接。
>
> 第一步是确认服务到底活没活。我用 `docker compose ps -a`——这里关键是加了 `-a`，因为不加的话只能看到正在运行的容器，而 nginx 已经退出了，不加这个参数我根本看不到它。加上之后看到 nginx 的状态是 `Exited (1)`，说明它是启动之后崩掉的。
>
> 第二步是看它为什么崩。`docker logs` 拉日志。日志里大部分是噪音，我只盯 `[crit]`、`[emerg]`、`[error]` 这几个级别和最后一行，找到关键报错：`[crit] prwrite() "/run/nginx.pid" failed (1: Operation not permitted)`。这是一个**系统调用被拒绝**的错误，不是配置语法错误——所以我判断问题不在我的 compose 文件里。
>
> 第三步是隔离变量。我把可能的原因列了四种：SELinux 拦截、文件系统权限、我自己的配置、镜像本身。然后一个一个排除：
>
> - `getenforce` 返回 Disabled，**排除 SELinux**；
> - 起一个 alpine 容器在 `/run` 目录下创建文件，成功了，说明容器里能正常写这个目录，**排除文件系统权限**；
> - 最后我起了个 nginx 容器，**完全不挂载我自己的配置文件**，结果报出一模一样的错——这一步是决定性的，它**排除了我的配置**。
>
> 三个实验做完只剩一种可能：nginx 这个镜像本身。根因是 `nginx:alpine` 这个新版本的二进制和 CentOS 7 的内核 3.10 不兼容，创建 pid 文件的时候被内核拒绝，跟我的配置没有任何关系。
>
> 确认不是自己的问题之后，我换了 `nginx:1.24-alpine` 这个老 tag，问题消失。这件事也让我定了一个止损原则：**环境级的怪问题，10 分钟内判断归属——确认不是自己的问题就绕过，不死磕。**

### 追问预案（评审方一定会问）

**Q1：你怎么确定不是你自己配置写错了？**
→ 因为最后一个实验里我**完全没有挂载自己的配置文件**，用的是镜像自带的默认配置，照样报错。配置这个变量已经被移除了。

**Q2：为什么排除 SELinux？**
→ `getenforce` 返回 Disabled，SELinux 根本没启用，不可能拦截。

**Q3：怎么判断那个 `[crit]` 是信号而不是噪音？**
→ 两个依据：一是它的级别是 `crit`（严重），二是它出现在启动流程的最后一步——进程在创建 pid 文件时死掉。日志里还有一条 `can not modify /etc/nginx/conf.d/default.conf (read-only file system?)`，那条是噪音，因为是我自己用 `:ro` 只读挂载配置导致的，属于预期行为。

**Q4：如果是你在生产环境遇到，你会怎么做？**
→ 一样的流程，但会多两步：一是确认这个镜像版本在其他节点上是否正常（判断是单机问题还是普遍问题）；二是如果确实要升级内核风险太大，就走"锁定可用版本"的路子，并在镜像仓库里把这个版本标记为可用基线。

### 这段经历里可迁移的方法论（技术问答加分项）

1. **`-a` 才能看到已退出的容器**——默认视图会骗你
2. **日志里 90% 是噪音**，只盯 `[crit]` / `[emerg]` / `[error]` 和最后一行
3. **隔离变量的实验条件必须和真实现场一致**——我最初用 `sh -c` 绕过 entrypoint 做过一次测试，实验设计本身有缺陷，结论不可用，后来重做了
4. **环境级怪问题要止损**：10 分钟判断归属，确认不是自己的问题就绕过
