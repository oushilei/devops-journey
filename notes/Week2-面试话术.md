## 话术 A · 我搭的一条完整 CI 流水线

### 参考版

> 我在 Jenkins 上搭了一条完整的 CI 流水线，从拉代码到镜像入库全自动，中间不需要人工干预。
>
> 环境是 Docker 里跑的 Jenkins LTS，用命名卷持久化配置和任务数据，装了 94 个插件。因为要构建镜像，我用 DooD 的方式让容器里的 Jenkins 能调用宿主机的 Docker。
>
> 流水线分四个阶段：从 GitHub 拉代码、多阶段构建镜像、推送到私有 registry、最后独立验证。整条跑完 15 秒左右，因为 Docker 分层缓存生效了。
>
> 触发方式有两种：手动参数化构建，或者 Poll SCM 自动检测代码变更。参数化是为了让同一份脚本服务不同分支和版本——我定义了分支和镜像 tag 两个参数，第一次构建产出 v1，第二次产出 v2，两个 tag 都在仓库里。
>
> 有个设计我想强调一下：**最后的验证阶段，我不看构建日志里的"成功"字样**，而是用 registry 的 API 查 tag 列表，确认镜像真的入库了。因为日志是客户端视角，说的是"我发出去了"，但服务端到底收没收到是另一回事。
>
> 这个原则是通用的：**每一个"完成"，后面都要跟一个独立的验证动作。**

### 追问预案

**Q1：为什么用 Docker 部署 Jenkins，不用裸机装？**
→ 三个原因：一是环境隔离，Jenkins 的 Java 版本、依赖不会污染宿主机；二是迁移方便，整个 Jenkins 就是容器加一个数据卷，换机器只要把卷迁过去；三是和我要管的环境一致——我后面要管的就是容器化的服务，自己先用容器跑起来更容易理解。

**Q2：命名卷和绑定挂载有什么区别，为什么选命名卷？**
→ 绑定挂载是把宿主机的一个具体路径挂进去，命名卷是 Docker 自己管理的存储。我选命名卷是因为不需要关心宿主机路径，而且容器删了数据还在。这一点我实际验证过：之前有个 registry 容器没挂卷，删掉之后里面的镜像全丢了。

**Q3：94 个插件是怎么算的？**
→ `ls /var/jenkins_home/plugins/*.jpi | wc -l`。注意插件目录里每个插件会有两个条目——一个 .jpi 文件和一个同名解压目录，所以 188 个条目实际是 94 个插件。

**Q4：这条流水线如果放到生产环境，还缺什么？**
→ 至少三块：一是多分支流水线，现在只覆盖 main 和 dev；二是构建失败的通知机制，现在失败了只能进 Jenkins 看；三是镜像 tag 策略，现在用 v1、v2 这种手工 tag，生产环境应该用 git commit hash 或语义化版本，保证可追溯。

## 话术 B · DooD：容器里的 Jenkins 怎么操作 Docker

> **这段是原理类，面试官问"你怎么部署的"时会用到。核心是把"为什么"讲清楚。**

### 参考版

> Jenkins 我部署在 Docker 容器里，但这里有个矛盾：Jenkins 需要执行 `docker build`，而它自己就在容器里，容器里没有 Docker 环境。
>
> 我用的方案叫 Docker-outside-of-Docker，简称 DooD。它的原理建立在一个前提上：**`docker` 命令本身只是个客户端，真正干活的是宿主机的 `dockerd` 进程**，两者通过 Unix socket 通信。所以只要让容器里的客户端能连上宿主机的 dockerd 就行。
>
> 具体做三件事：
>
> 第一，把宿主机的 `/var/run/docker.sock` 挂进容器，让容器里的客户端有通信通道；
> 第二，容器镜像里没有 `docker` 命令，我从宿主机把它拷贝进去；
> 第三，socket 文件属于宿主机的 docker 组，而容器里的 jenkins 用户不在这个组里，所以要用 `--group-add` 把宿主机的 docker 组 GID 加进去，否则会报权限拒绝。
>
> 这三步缺一不可。我当时是先做前两步，执行 `docker ps` 报权限错误，才补上第三步的——`docker exec jenkins docker ps` 能看到宿主机的所有容器，说明打通了。
>
> 另一个选择是 Docker-in-Docker，就是在容器里再跑一个 dockerd。但那样需要特权模式，镜像层要重新下载，资源开销大得多。DooD 更轻，代价是容器里的 Jenkins 对宿主机 Docker 有完全控制权，这是个需要接受的信任边界。

### 追问预案

**Q1：为什么挂 socket 就够了？**
→ 因为 Docker 是 C/S 架构。客户端把命令通过 socket 发给 daemon，daemon 执行完把结果返回。挂上 socket 之后，容器里的客户端发出去的请求，实际上是宿主机 daemon 在处理——所以构建出来的镜像存在宿主机上，容器里也能看到。

**Q2：`--group-add 995` 这个 995 是哪来的？**
→ 宿主机上 docker 组的 GID，用 `getent group docker` 能查到。容器里的进程要访问 socket 文件，必须有对应的组权限。这个数字在不同机器上可能不一样，所以不能写死。

**Q3：DooD 有什么风险？**
→ 最大的风险是权限过大——容器里的 Jenkins 能操作宿主机的全部 Docker 资源，包括删除容器、查看其他容器的数据。如果 Jenkins 被入侵，等于宿主机 Docker 被控制。生产环境通常会用受限的 socket 代理，或者干脆用 Kubernetes 的 Pod 模式跑构建，不用 DooD。

**Q4：怎么验证 DooD 配好了？**
→ `docker exec jenkins docker ps`，能列出宿主机的容器就说明通了。这个命令的语义很关键：`docker exec` 是进容器，`docker ps` 是容器里的客户端去问宿主机的 daemon——一条命令同时验证了"能进容器"和"容器能操作宿主机 Docker"。

## 话术 C · 凭据管理：密码怎么不泄露

> **这段是安全类，任何涉及 CI/CD 的面试都会问。**

### 参考版

> 推镜像需要仓库密码，而密码绝对不能写在 Jenkinsfile 里——因为 Jenkinsfile 本身要提交到 Git，密码就永久留在版本历史里了，而且改密码要改所有分支，谁 clone 仓库都能看到。
>
> 我的做法是用 Jenkins 的 Credentials 功能，它是三层机制：
>
> **第一层是存储**：密码加密存在 Jenkins master 端，流水线里只引用一个 credentialsId，代码里不出现明文。
>
> **第二层是注入**：在 environment 块里用 `credentials('id')` 绑定，它会自动生成两个环境变量——用户名是 `_USR` 后缀，密码是 `_PSW` 后缀。这里我踩过一个坑：`parameters` 定义的参数在 `sh` 里不一定取得到值，所以我改成在 environment 里显式映射，并用 Elvis 运算符给默认值兜底。
>
> **第三层是打码**：Jenkins 会把凭据的值登记进掩码列表，构建日志里任何匹配到的字符串都自动替换成 `****`。我在日志里看到的实际效果是 `+ echo ****`——我写的是 `echo "$REGISTRY_CRED_PSW"`，输出被打了码。
>
> 传输环节我用 `--password-stdin` 而不是 `-p`，因为 `-p` 会把明文密码写进 `~/.bash_history`，`ps` 也能看到。最后在 `post` 的 `always` 阶段执行 `docker logout`，清理掉登录凭据——因为 `docker login` 会把凭据写进 `~/.docker/config.json`，是 base64 编码而不是加密。

### 追问预案

**Q1：Jenkins 的凭据存在哪？加密吗？**
→ 存在 master 的 `$JENKINS_HOME/credentials.xml`，里面的值是加密的，加密密钥在 master 的密钥文件里。所以单拿走 credentials.xml 也解不开。

**Q2：生产环境你会怎么做？**
→ 更推荐用外部密钥管理，比如 HashiCorp Vault 或 K8s Secret，Jenkins 只做中转。因为 Jenkins 凭据的加密密钥和密文在同一台机器上，如果整机被拿下，凭据就等于泄露了。

**Q3：`credentials()` 生成的变量名为什么要加后缀？**
→ 因为一个凭据包含两个值（用户名和密码），Jenkins 用 `_USR` 和 `_PSW` 后缀区分。这个后缀是固定的，写成 `_USER` 或 `_PASS` 取不到值。

**Q4：`docker login` 之后不 logout 会怎样？**
→ 凭据留在 `~/.docker/config.json` 里，后续任何在这个环境里跑的构建都能复用这个登录态。如果多个团队共用构建机，等于 A 团队的凭据被 B 团队用了。

## 话术 D · 自动触发：内网环境怎么实现"提交即构建"

> **这段是选型类，重点展示你"能根据约束选方案"的判断力。**

### 参考版

> 代码提交后自动构建，标准做法是 Webhook——GitHub 收到 push 时主动发一个 HTTP 请求通知 Jenkins。它是实时的，秒级触发。
>
> 但它有个硬性前提：**Jenkins 必须能被公网访问到**。而我的环境是内网 IP，GitHub 的服务器在公网，根本路由不进来。这里有个容易混淆的点：我的 Jenkins **能**访问公网——不然拉代码怎么成功——但反过来"被公网访问"是另一个方向，这两件事不是一回事。
>
> 所以我用的是 Poll SCM，反过来让 Jenkins 定时去问 GitHub。配置就是一个 cron 表达式，我写的是每 5 分钟轮询一次。
>
> 轮询的机制是：用 `git ls-remote` 问远程最新的 commit 哈希，和自己这边"上次成功构建的 revision"对比，不同就触发构建。
>
> 这里有个细节我实际遇到过：**基准是"上次成功构建"，不是"上次构建"**。有一次构建失败了，5 分钟后轮询又触发了一次。原因是失败不推进基准，相当于自动重试——这是有意设计的，否则那次提交就永远不会被构建，代码会被漏掉。
>
> 还有一个发现值得说：**轮询成功不代表构建能拉下来**。轮询用的是 `ls-remote`，只查引用列表，几百字节，0.97 秒就完成；但构建用的是 `git fetch`，要传几 MB 的对象，连接维持时间长，网络不稳的时候更容易断。我确实遇到过轮询正常、构建时报 TLS 连接中断的情况。

### 追问预案

**Q1：为什么不用 `*/5` 而是 `H/5`？**
→ `H` 是 Jenkins 特有的 Hash 符号，不是标准 cron 语法。它会根据 job 名称算出一个稳定的偏移量，让多个 job 的触发时间自动错开。如果所有 job 都写 `*/5`，它们会在 0 分、5 分、10 分同时发请求，形成尖峰，容易被 GitHub 限流。

**Q2：轮询有延迟，生产环境能接受吗？**
→ 看场景。对持续集成来说，5 分钟延迟通常可以接受，因为 CI 的目的是尽早发现问题，不是抢时间。但如果是要求秒级响应的场景，就必须上 Webhook——通常做法是给 Jenkins 配一个公网入口，或者用内网的 GitLab 代替 GitHub，GitLab 和 Jenkins 在同一内网就能直接回调。

**Q3：轮询会不会很耗资源？**
→ 会。99% 的轮询结果都是"没变化"，属于无效请求。而且 GitHub 对未认证请求限流每小时 60 次每 IP，轮询频率太高会撞上限流。所以轮询是"没有公网时的退路"，有条件的话优先 Webhook。

**Q4：如果 Jenkins 和 GitHub 网络一直不稳怎么办？**
→ 我实际排查过一个报错：`GnuTLS recv error (-110): The TLS connection was non-properly terminated`，这是 TLS 连接被非正常中断，属于网络层问题。判断依据很简单——同一个配置上次能拉、这次不能拉，那就是网络问题，不要往配置上找。解决办法是给容器配代理，或者改用国内代码托管。

## 快问快答（应对连续追问）

| 面试官问 | 一句话答 |
|---|---|
| Jenkins 的 Pipeline 和 FreeStyle 有什么区别？ | Pipeline 是代码化的流水线，能进版本控制、能评审、能复用；FreeStyle 是网页点选，无法版本化，改起来只能靠人记 |
| 声明式和脚本式 Pipeline 选哪个？ | 优先声明式——结构固定、语法检查更早、可读性好；需要复杂逻辑（循环、条件）时用 `script` 块嵌入 |
| `post` 有哪些分支？ | always / changed / fixed / regression / aborted / failure / success / unstable / cleanup，共 9 个 |
| 阶段失败了后面的阶段会怎样？ | 默认跳过，日志显示 `skipped due to earlier failure(s)`；`post` 里的 `always` 仍会执行 |
| `parallel` 有什么用？ | 把无依赖的阶段并行执行。我实测过串行 16 秒、并行 5 秒 |
| Jenkins 容器重启后任务会丢吗？ | 不会。任务数据在 `$JENKINS_HOME` 里，只要挂了卷就保留；容器配置也存在元数据里，`docker start` 就能按原配置恢复 |

## 本段话术里的可迁移方法论（面试加分项）

1. **验证要落在外部可观测的事实上** —— 不看日志的"成功"字样，用 registry API 查 tag 列表。日志是过程，产物是结果。
2. **改配置前先读原文件** —— 改 `daemon.json` 时如果直接覆盖，会丢掉 K8s 要求的 `cgroupdriver` 配置。这个习惯避免了一次集群故障。
3. **小数据量能通 ≠ 大数据量能通** —— `ls-remote` 能通不代表 `fetch` 能通；`ping` 能通不代表下载能通。
4. **判断网络问题的依据是"对比"** —— 同一配置上次能、这次不能，就是网络问题，不要往配置上找。
5. **根据约束选方案，而不是选最"标准"的方案** —— Webhook 更标准，但内网环境用不了，所以选 Poll SCM。能说清"为什么不选另一个"比"用了哪个"更重要。
