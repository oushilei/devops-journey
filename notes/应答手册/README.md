# 技术应答手册 · 总纲

> 用途：把 W1~W6 做过的事，整理成**能被连续追问三层而不崩**的材料。
> 不是背稿，是**每答一句，都留得下下一层追问**。

---

## 一、这份手册怎么用

### 三层结构（每个模块都一样）

| 层 | 回答什么问题 | 答不出的后果 |
|---|---|---|
| **原理层** | "它为什么这么设计？底层怎么实现的？" | 只能复述操作，一问就露 |
| **项目层** | "你实际做过什么？数据是多少？踩过什么坑？" | 讲不出细节，像抄的 |
| **排障层** | "线上出现 X 现象，你怎么查？" | 只会部署不会救火 |

**三层的关系**：原理决定你排障时的**搜索空间**。不懂原理，排障就是碰运气。

### 标记约定

| 标记 | 含义 |
|---|---|
| **【实测】** | 我在自己环境里跑过、看到过输出，数据可复现 |
| **【通用】** | 行业标准做法/常识，我没有亲自验证过 |
| **【未验证】** | 我的推断，逻辑上成立但没实测 —— **被追问时要主动说这句** |

> 这条约定是纪律：**把推断当事实讲，是应答里最致命的问题**。宁可说"这块我没实测"，也不要编一个像样的答案。

### 自测方法

每个模块末尾有 8 道闭卷题。做法：

1. 合上文档，口头答（不要写，说出来的才算）
2. 答完再看原文对照
3. **答不出的题目标红**，第二天只复习红题
4. 连续两轮全绿才算这个模块过关

## 二、五个模块的边界

| 模块 | 覆盖 | 不覆盖（被问到要主动划界） |
|---|---|---|
| 01 Docker | 镜像分层、容器本质、网络、存储、多阶段构建 | Swarm、K8s 之外的编排、镜像签名 |
| 02 CI/CD | GitLab CI 模型、Runner、artifacts/cache、四道门禁 | Jenkins 深入、ArgoCD/GitOps、多环境发布策略 |
| 03 Kubernetes | Deployment/RS/Pod、探针、Service、滚动、回滚、RBAC | Ingress、StatefulSet、Operator、网络插件原理、etcd 运维 |
| 04 监控告警 | Prometheus 数据模型、三类 exporter、PromQL 基础、告警规则 | Alertmanager 路由、长期存储、Loki/链路追踪 |
| 05 故障处置 | 判定顺序、回滚决策、复盘写法 | 生产值班流程、跨团队协作、SLA 管理 |

**划界不是示弱，是准确**。说"这块我没碰过"比硬答一个错的强十倍。

## 三、所有数字的总表（背下来）

这些是六周实测出来的硬数据，**每个数字都要能说出怎么测的**。

| 数据 | 值 | 怎么来的 |
|---|---|---|
| 镜像体积 | **884MB → 14.1MB**（62.7 倍） | 单阶段 node 基础镜像 vs 多阶段 + nginx alpine |
| Jenkins 流水线耗时 | **34 秒**全绿 | DooD 模式，容器内调宿主机 daemon |
| GitLab Runner 并发 | `concurrent=1` → `2`，同 stage 两 job **57s → 28s** | 实测两个 job 从排队变并行 |
| 槽位排队 | 3 个 job 抢 2 槽位 → 第三个 `Queued 28s / Duration 0s` | 并发上限的实证 |
| cache 命中 | 首次 `CACHE MISS` 5s → 二次 `CACHE HIT` 1s | 同一 commit 重跑 |
| 镜像 tag | 双 tag（sha + latest）指向**同一 digest** | `docker push` 第二次全 `Layer already exists` |
| 探针对照（无探针） | 坏镜像 → `1/1 Running` + `successfully rolled out` + **HTTP 全 000** | **假成功** |
| 探针对照（有探针） | 坏镜像 → 新 Pod `0/1` + `timed out` + **HTTP 全 200** | 探针把坏版本挡在流量外 |
| revision 编号 | `undo` 后 **REV 15 → 17**，但 RS 的 CREATED 不变 | 编号是记账，不是对象年龄 |
| `revisionHistoryLimit` | 10 → 1，RS 从 3 个变 2 个（删掉 REV 2/3/5） | 按 revision 号删，不按创建时间 |
| scrape target | **4 个全 up** | prometheus / node / k8s-cadvisor / kube-state-metrics |
| 指标条数 | `kube_*` **1102** / `container_*` **1761** / node samples **943** | `curl .../metrics \| grep -c` |
| 告警实测 | `Inactive → Pending → Firing(1) → 恢复` | `docker stop node-exporter` 触发 |
| 故障演练 | 流水线红 + **HTTP 200 全程** + 原有告警**不响** | 注入"进程活着但探针不通"的坏版本 |
| 端到端时间戳 | Pod 启动 UTC 13:27:49/59 → 监控序列首点 21:28/21:30（北京） | 两套独立数据源对齐，差 1~2 分钟 |

## 四、三个"必须主动说"的边界

每次被问到项目，**主动**把这三条说清楚，比等对方问出来强：

1. **环境是 2 台虚拟机的实验环境**，单集群、单地域、无真实流量、无 SLA、无值班组织。
   → 验证的是**机制能跑通**，不是"扛得住"。

2. **能采集 ≠ 能告警**。我的告警规则只有 2 条（`TargetDown` / `PodNotReady`），
   真实生产环境的规则数量是几十到几百条，覆盖业务指标、中间件、证书、容量。

3. **没有碰过的东西**：Ingress、StatefulSet、Helm、GitOps、云平台、Alertmanager 通知路由、
   生产值班流程。**这些不是"了解"，是"没做过"**。
