# 04 · 监控与告警

> 核心一句话：**采集是照单全收，判断在查询和规则里。Prometheus 本身不懂"故障"这个词。**
> 这句话能解释 80% 的监控排障题。

---

## 0. 一分钟版本

> 我用 Prometheus + Grafana 搭了监控栈，接了三个采集源：node_exporter 看主机（943 个样本）、cAdvisor 看容器（经 apiserver proxy，1761 条 `container_*`）、kube-state-metrics 看 K8s 对象状态（1102 条 `kube_*`）。四个 target 全 up。写了告警规则 `up == 0` + `for: 1m`，并真的触发过一次——`docker stop node-exporter` 后状态从 `Inactive` → `Pending`（观察期）→ `Firing`，恢复后回到 `Inactive`。后来在故障演练里发现：**target 全 up 时故障照样存在，因为规则只覆盖了采集层**，又补了 `PodNotReady`。

## 一、原理层

### 1.1 为什么是 pull 而不是 push

| | pull（Prometheus 主动拉） | push（应用推） |
|---|---|---|
| 谁控制节奏 | **服务端** | 客户端 |
| 服务挂了怎么知道 | **拉不到 = `up=0`**，天然自带 | 需要额外的心跳机制 |
| 客户端要改配置吗 | 不用，只要暴露 `/metrics` | 要配服务端地址 |
| 跨网络/防火墙 | 服务端要能访问目标 | 客户端要能出网 |
| 短任务（批处理） | **拉不到**（跑完就没了） | 能推 |

**为什么 Prometheus 选 pull**：最关键的收益是 **`up` 这个指标**——"我能不能拉到"本身就是最重要的健康信号，push 模型里没有这个天然信号。

**pull 的代价**：短生命周期任务（CronJob）拉不到，需要 **Pushgateway** 中转。这块我没做过。

### 1.2 数据模型：时间序列

```
指标名{标签1="值1", 标签2="值2"} → [(时间戳, 数值), ...]
```

**唯一标识一条序列的是"指标名 + 全部标签"**。这个理解决定了三件事：

| 现象 | 原因 |
|---|---|
| `by (pod_name)` 得到 1 条序列 | `pod_name` 这个标签不存在，所有数据被聚成一组 |
| 加一个高基数标签导致内存暴涨 | 每条不同标签组合都是一条独立序列 |
| 两个看板同一个指标数值不同 | 聚合方式（`sum`/`avg`/`by`）不同 |

**标签基数的量级感**（这是被问"监控为什么慢/爆内存"的答案）：

```
100 个 Pod × 20 个指标 × 10 个标签维度 = 2 万条序列
如果再加一个"请求 URL"标签，1000 个 URL → 2000 万条序列 → 直接压垮
```

> **原则：不要给指标加高基数标签**（用户 ID、URL、request ID）。这类数据该进日志，不该进指标。

### 1.3 四种指标类型

| 类型 | 特征 | 典型例子 | 怎么用 |
|---|---|---|---|
| **Counter** | **只增不减**（重启归零） | 请求总数、错误数、重启次数 | 必须用 `rate()` / `increase()` 才有意义 |
| **Gauge** | 可增可减 | CPU 使用率、内存占用、副本数 | 直接看值，或 `avg_over_time()` |
| **Histogram** | 分桶统计（`_bucket`/`_sum`/`_count`） | 请求延迟分布 | `histogram_quantile()` 算分位数 |
| **Summary** | 客户端算好的分位数 | 延迟 P99 | 直接读，但不能跨实例聚合 |

**最容易错的一点**：把 Counter 直接画图 → 看到一条一直上升的斜线，毫无意义。

```promql
# 错：直接画 counter
kube_pod_container_status_restarts_total

# 对：看"过去 5 分钟新增了多少次"
increase(kube_pod_container_status_restarts_total[5m])
```

### 1.4 `rate` / `increase` / `irate` 的区别

| 函数 | 返回 | 用途 |
|---|---|---|
| `rate(x[5m])` | **每秒**平均增长率 | QPS、错误率 |
| `increase(x[5m])` | 区间内**总增量** | "5 分钟重启了几次" |
| `irate(x[5m])` | 用**最后两个点**算瞬时速率 | 快速变化的曲线（抖动大） |

**一个必须知道的坑**：`rate()` 在窗口内**至少需要两个样本**。如果 `scrape_interval=15s` 而窗口是 `[30s]`，只有 2 个点，结果会很不稳定。**经验：窗口至少是抓取间隔的 4 倍。**

### 1.5 `up` 到底代表什么（这题经常答错）

```promql
up{job="node"} = 1
```

**它的含义不是"服务健康"，而是"这次抓取返回了 HTTP 2xx"。**

| 情况 | `up` | 实际含义 |
|---|---|---|
| 正常 | 1 | 抓取成功 |
| 目标挂了 | 0 | 连接失败 / 超时 |
| 返回 404 | **0** | 路径写错了（不是"有数据"） |
| 返回 500 | **0** | 服务端报错 |
| **抓到了但页面是空的** | **1** ⚠️ | **最危险**：通了，但没数据 |

**所以 `up=1` 不等于"有数据"**。要判断"是否真的有数据"，配合：

```promql
scrape_samples_scraped{job="node"}     # 这次抓到了多少个样本
# = 0 且 up = 1 → 通了但空，最危险的状态
```

> **这条是 W5 最重要的认知**：`up` 只告诉你"HTTP 通了"，不告诉你"数据有没有"。

### 1.6 告警的状态机

```
inactive（条件不满足）
   ↓ 条件开始满足
pending（条件满足，但在 for 的观察期内）
   ↓ 持续满足超过 for
firing（正式告警）
   ↓ 条件不再满足
inactive
```

**`for` 的作用**（这是被问"怎么防误报"的标准答案）：

> 网络抖一下、容器重启的几秒空窗、一次 GC 卡顿——这些都会让条件**短暂**满足。
> `for` 要求"持续满足一段时间"，把瞬时抖动过滤掉。

**代价**：真实故障的发现也会延迟 `for` 的时长。所以 `for` 是**误报率和发现延迟之间的取舍**，不是越大越好。

**我的实测**：

| 时刻 | 状态 |
|---|---|
| `docker stop node-exporter` 刚执行 | `inactive` → `pending` |
| 30 秒后 | **`pending`**（`for: 1m` 没走完，不报） |
| 70 秒后 | **`firing`**，`value=0`，`instance=192.168.245.150:9100` |
| `docker start` 后 | `inactive` |

### 1.7 三个采集源的分工（K8s 环境下必问）

| 采集源 | 数据来自 | 回答什么问题 | 我的量级 |
|---|---|---|---|
| **node_exporter** | 宿主机 `/proc`、`/sys` | 机器 CPU/内存/磁盘/网络 | 943 个样本 |
| **cAdvisor** | kubelet 内置（容器运行时数据） | **容器用了多少资源** | 1761 条 `container_*` |
| **kube-state-metrics** | **watch apiserver** | **对象现在是什么状态** | 1102 条 `kube_*` |

**一句话区分 cAdvisor 和 kube-state-metrics**：

> **cAdvisor 回答"用了多少"，kube-state-metrics 回答"是什么状态"。**
> 前者是数值（CPU 用了 200m），后者是状态（这个 Pod Ready 还是没 Ready）。

**为什么 kube-state-metrics 这么重要**：`RESTARTS`、`CrashLoopBackOff`、副本 `0/1`、`Pending` —— **这些只有它能变成指标**。cAdvisor 完全看不到"对象状态"。

### 1.8 cAdvisor 为什么要走 apiserver proxy

| 路径 | 结果 |
|---|---|
| 直连 `https://node:10250/metrics/cadvisor` | **401**（kubelet 需要认证） |
| 走 apiserver proxy：`https://master:6443/api/v1/nodes/<node>/proxy/metrics/cadvisor` | **200**（用 token 认证） |

**代价**：流量绕一圈（Prometheus → apiserver → kubelet），且 apiserver 成为瓶颈。生产上更常见的做法是 kubelet 直接暴露只读端口或用 ServiceMonitor。

### 1.9 TSDB 存储的常识

| 项 | 值 |
|---|---|
| 本地存储默认保留 | 15 天（`--storage.tsdb.retention.time`） |
| 数据块 | 每 2 小时一个 block |
| 压缩 | 后台自动 compaction |
| 内存中 | 最近 2 小时在 head block（内存 + WAL） |

**代价**：Prometheus **不是长期存储**。要做长期存储（几个月/几年）需要 remote write 到 Thanos/VictoriaMetrics/M3。**这块我没做过。**

## 二、项目层

### 2.1 最终环境

| 组件 | 版本/端口 | 状态 |
|---|---|---|
| Prometheus | 2.45 / **9090** | ✅ 4 个 target 全 up |
| node_exporter | **9100** | ✅ 943 样本 |
| cAdvisor | 经 apiserver proxy | ✅ 1761 条 `container_*` |
| kube-state-metrics | v2.9.2 / **18080** | ✅ 1102 条 `kube_*` |
| Grafana | 10.2.0 / **3000** | ✅ 看板 1860 + 7249 |

**为什么 kube-state-metrics 用 18080**：8080 被 W2 的 Jenkins 占了。这类"端口冲突"在生产上也很常见，处置方式就是换映射端口（`-p 18080:8080`）。

### 2.2 四个 target 的配置

```yaml
scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']

  - job_name: 'node'
    static_configs:
      - targets: ['192.168.245.150:9100']

  - job_name: 'k8s-cadvisor'
    scheme: https
    metrics_path: /api/v1/nodes/k8s-node1/proxy/metrics/cadvisor
    bearer_token_file: /etc/prometheus/k8s.token
    tls_config:
      insecure_skip_verify: true
    static_configs:
      - targets: ['192.168.245.133:6443']

  - job_name: 'kube-state-metrics'
    static_configs:
      - targets: ['192.168.245.150:18080']
```

**注意 `metrics_path` 里写死了 `k8s-node1`**——只抓一个节点。生产用 `kubernetes_sd_configs` 自动发现所有节点。**这是我的环境与生产的差距之一。**

### 2.3 告警规则（最终 2 条）

```yaml
groups:
  - name: basic
    rules:
      - alert: TargetDown
        expr: up == 0
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.job }} 抓不到了"

      - alert: PodNotReady
        expr: kube_pod_status_ready{condition="false",namespace="default"} == 1
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.pod }} 持续 1 分钟未就绪"
```

**第二条的细节值得展开**（这是被追问"为什么这么写"的点）：

`kube_pod_status_ready` 对每个 Pod 固定输出 **3 行**：

```
pod A: condition="true"    → 1 或 0
pod A: condition="false"   → 0 或 1
pod A: condition="unknown" → 0 或 1
```

**所以必须写 `condition="false" == 1`**，不能写 `kube_pod_status_ready == 0`——后者会把 `true`/`unknown` 的 0 也算进去，产生大量误报。

### 2.4 「看板会骗人」的实例（这是最有价值的一条）

**现象**：7249 看板的 `Top 5 Memory Intense Pods` 显示 `4.55 GiB`，但另一个面板显示单个容器只有 `937 MiB`。看起来矛盾。

**排查**：点面板 → Edit → 看 `expr`：

```promql
topk(5, sum(container_memory_usage_bytes{image!=""}) by (pod_name))
```

**根因**：`pod_name` 这个标签**在新版 cAdvisor 里已经改名成 `pod`**。

| 分组方式 | 得到的序列数 |
|---|---|
| `by (pod_name)` | **1 条**（标签不存在，所有容器被聚成一组） |
| `by (pod)` | **5 条**（正确） |

所以那个 `4.55 GiB` 是**所有容器内存的总和**，不是"某个 Pod 用了 4.55 GiB"。返回的 `metric` 甚至是空的 `{}`。

> **比 `No data` 更危险的是"看起来正常但算错了的曲线"**——前者一眼就知道没数据，后者会让你做出错误判断。
> **判据：数值看着不对，第一反应是点开 Edit 看 `expr`。**

### 2.5 看板选择（为什么是 7249）

对比了 4 个社区 K8s 看板，按"本机指标覆盖率"排：

| ID | 依赖指标数 | 本机有 | 判断 |
|---|---|---|---|
| 6417 | 25 | 11 | ❌ 需要一堆没有的组件 |
| 13332 | 31 | 18 | ⚠️ 一半空 |
| 8588 | 17 | 8 | ❌ |
| **7249** | **8 个核心指标全有** | ✅ 全覆盖 | **选它** |

**方法论**：导看板前先算"它依赖的指标我有几个"，而不是导完看哪里空。**这个动作在生产上同样适用。**

### 2.6 踩过的坑

| # | 坑 | 根因 | 修法 |
|---|---|---|---|
| 1 | token 文件容器读不到 | 容器以 `nobody(65534)` 跑，文件是 `600 root` | `chown 65534:65534` + `600` |
| 2 | 8080 被 Jenkins 占用 | 端口冲突 | 映射到 18080 |
| 3 | kube-state-metrics 刷 Forbidden | 默认 watch 所有对象类型，权限不够 | `--resources=` 限制范围 |
| 4 | 7249 内存面板数值离谱 | 标签改名（`pod_name` → `pod`） | 知道即可，改 `expr` 才能修 |
| 5 | 镜像拉不到（8 个地址全失败） | 国内源前缀拼错（`docker.m.daocloud.io/registry.k8s.io/...`） | 正确是 `m.daocloud.io/registry.k8s.io/...` |
| 6 | 告警没触发但以为触发了 | `grep -o '"labels":{[^}]*}'` 里 `{` 被当正则区间起始 | 改用 `tr ',' '\n' \| grep` |

**第 1 条的完整逻辑**（很值得讲）：

```
Prometheus 容器以 nobody(65534) 运行
  → 读 /etc/prometheus/k8s.token
  → 文件是 root:root 600 → 读不到 → cAdvisor job 401
  → 改成 644 能读，但宿主机任何人可见 token（不安全）
  → 正确：chown 65534:65534 + chmod 600
```

## 三、排障层（现场题）

### 3.1 「target DOWN」五步法（这是我的速查表）

```bash
# 1) 看状态和错误
curl -s http://localhost:9090/api/v1/targets | grep -o '"health":"[^"]*"\|"lastError":"[^"]*"'

# 2) 按 lastError 分类
# 3) 在 Prometheus 容器内手动 curl 一次（排除容器网络问题）
docker exec prometheus wget -qO- --timeout=3 http://<target>:<port>/metrics | head -3

# 4) 检查认证（需要 token 的 job）
# 5) 检查配置是否生效（reload 了吗）
curl -X POST http://localhost:9090/-/reload
```

**`lastError` 分类表**：

| lastError 关键词 | 原因 | 处置 |
|---|---|---|
| `connection refused` | 目标没监听 / 进程挂了 | 查目标服务状态 |
| `context deadline exceeded` | 超时（网络不通或太慢） | 查防火墙、MTU、目标负载 |
| `401 Unauthorized` | 认证失败 | 查 token 文件权限/内容 |
| `403 Forbidden` | 权限不足 | 查 RBAC |
| `404 Not Found` | **路径写错**（`metrics_path`） | 核对路径 |
| `x509: certificate` | 证书问题 | `insecure_skip_verify` 或换 CA |
| `server returned HTTP status 500` | 目标自身报错 | 查目标日志 |
| `no such host` | DNS | 查解析 |

> **`404` 有个反直觉点**：它会让 `up=0`，但目标其实是活的。**"目标活着但配置错了"和"目标挂了"是两件事**，`lastError` 能区分。

### 3.2 「`up=1` 但图上是空的」

```promql
# 1) 真的有样本吗
scrape_samples_scraped{job="xxx"}

# 2) 指标名对不对（大小写、前缀）
{__name__=~".*memory.*"}       # 模糊找一下真实名字

# 3) 时间范围对吗
# 4) 看板的变量选对了吗（$instance / $node）
```

| 检查 | 结论 |
|---|---|
| `scrape_samples_scraped = 0` | 抓到了页面但没解析出指标 → 路径错或格式不对 |
| 指标名不存在 | 版本升级改名了（如 `pod_name` → `pod`） |
| 有数据但图空 | 看板变量没选 / 时间范围不含数据 |

### 3.3 「告警不响」

按这个顺序（**从条件到通知，逐层排除**）：

```bash
# 1) 规则加载了吗
curl -s http://localhost:9090/api/v1/rules | grep -o '"name":"[^"]*"\|"health":"[^"]*"'

# 2) 条件现在成立吗（手动跑一下 expr）
curl -sG --data-urlencode 'query=<你的 expr>' http://localhost:9090/api/v1/query

# 3) 状态是什么（inactive/pending/firing）
curl -s http://localhost:9090/api/v1/alerts

# 4) for 走完了吗（activeAt 时间）
# 5) 有 Alertmanager 吗（没有的话只有 Firing，不会发通知）
```

**判定表**：

| 现象 | 原因 |
|---|---|
| `rules` 里没有这条 | 规则文件没加载 / `rule_files` 路径错 / 没 reload |
| 有规则但 `health: err` | 表达式语法错（`promtool check rules` 能提前发现） |
| 条件成立但一直 `inactive` | 表达式写错（比如 `== 0` 写成了 `= 0`） |
| 一直 `pending` | `for` 太长，或者条件在反复横跳 |
| `firing` 但没收到通知 | **没装 Alertmanager**（我这就是） |

> **最后一条是我环境的真实缺口**：只有 `Firing`，没有通知渠道。**"告警响了但没人知道"和"没有告警"在生产上等价**。

### 3.4 「基数爆炸 / Prometheus 内存暴涨」

```promql
# 哪个指标序列最多
topk(10, count by (__name__) ({__name__=~".+"}))

# 哪个标签基数最高
count(count by (pod) (container_memory_usage_bytes))
```

| 原因 | 处置 |
|---|---|
| 加了高基数标签（URL、request_id） | 删掉该标签，改打日志 |
| `honor_labels` 导致标签冲突 | 调整配置 |
| 抓取目标数量暴增 | 加 relabel 过滤 |
| 保留时间太长 | 缩短 retention |

### 3.5 「时间不同步导致监控异常」

| 现象 | 原因 |
|---|---|
| 图表时间轴错乱 | Prometheus 与目标时钟差太多 |
| `x509: certificate has expired` | 证书校验依赖时间，时钟漂移后"未来/过去" |
| 数据点稀疏 | 抓取时间戳异常 |

**我的环境**：虚拟机挂起/恢复后时钟必漂移，装了 chrony 同步 `ntp.aliyun.com`。**这不是监控问题，是基础设施问题，但会以监控异常的形式表现出来。**

## 四、追问清单

**Q1：Prometheus 为什么用 pull 不用 push？**
→ pull 让"能否拉到"本身成为健康信号（`up`），push 模型没有这个天然信号。而且服务端控制节奏，客户端只要暴露 `/metrics`。
→ 再追"pull 有什么缺点"：短生命周期任务（CronJob）拉不到，要 Pushgateway 中转；跨防火墙要服务端能访问目标。

**Q2：`up=1` 说明服务健康吗？**
→ 只说明**这次抓取返回了 HTTP 2xx**，不代表有数据、更不代表业务健康。
→ 再追"那怎么判断有数据"：看 `scrape_samples_scraped`。**`up=1` 且 `scrape_samples_scraped=0` 是最危险的状态——通了但空。**

**Q3：Counter 和 Gauge 的区别？为什么 Counter 不能直接画图？**
→ Counter 只增不减（重启归零），直接画是一条上升斜线，没有信息量。必须用 `rate()` 或 `increase()` 转成"速率/增量"。Gauge 可增可减，直接看值。
→ 再追"`rate` 和 `increase` 区别"：`rate` 返回**每秒**速率，`increase` 返回**区间总增量**。看"重启了几次"用 `increase`。

**Q4：`for: 1m` 是干什么的？**
→ 防抖。条件要**持续满足 1 分钟**才从 `pending` 变 `firing`，过滤掉瞬时抖动。
→ 再追"代价是什么"：真实故障的发现也延迟 1 分钟。**是误报率和发现延迟的取舍。**

**Q5：cAdvisor 和 kube-state-metrics 有什么区别？**
→ cAdvisor 来自 kubelet，回答"容器用了多少资源"（数值）；kube-state-metrics watch apiserver，回答"对象是什么状态"（副本数、Ready、重启次数）。
→ 再追"哪个能看 Pod 重启"：kube-state-metrics 的 `kube_pod_container_status_restarts_total`。cAdvisor 看不到重启次数。

**Q6：为什么 cAdvisor 要走 apiserver proxy？**
→ kubelet 的 10250 需要认证，直连返回 401。走 apiserver proxy 可以复用 apiserver 的认证（token）。
→ 再追"代价"：流量绕一圈，apiserver 成瓶颈。生产上常用 kubelet 只读端口或 ServiceMonitor。

**Q7：target 显示 DOWN，你怎么查？**
→ 五步：看 `lastError` → 按错误分类（refused/timeout/401/404）→ 在容器内手动 curl 排除网络 → 查认证 → 确认配置 reload 了。
→ 再追"404 算 DOWN 吗"：算，`up=0`。但目标其实活着，是**路径配错了**。所以要看 `lastError` 区分"目标挂了"和"配置错了"。

**Q8：看板上的数字看着不对，怎么办？**
→ 点面板 → Edit → 看 `expr`。我踩过一个：7249 用 `by (pod_name)`，新版 cAdvisor 标签叫 `pod`，结果所有容器被聚成一条，显示 4.59 GiB 而不是单个 Pod。
→ 再追"为什么这比 No data 危险"：No data 一眼能看出没数据，**算错的曲线看起来正常**，会误导判断。

**Q9：怎么防告警风暴？**
→ 分级（P0/P3）、分组（同一原因的合并）、抑制（上游故障时压制下游告警）、静默（维护窗口）。
→ 再追"你做过吗"：**没做过**。我只做到 `Firing`，Alertmanager 的路由/分组/抑制都没配。

**Q10：指标基数太大会怎样？怎么控制？**
→ 内存和磁盘暴涨、查询变慢，严重时 Prometheus OOM。控制：不加高基数标签（URL/user_id）、用 relabel 丢弃、缩短 retention。
→ 再追"怎么看谁占得多"：`topk(10, count by (__name__) ({__name__=~".+"}))`。

**Q11：Prometheus 能存多久？长期存储怎么办？**
→ 默认本地 15 天。长期存储要 remote write 到 Thanos/VictoriaMetrics/M3。
→ 再追"你做过吗"：**没做过**，我只用了本地存储。

**Q12：告警响了但没人处理，问题在哪？**
→ 三个可能：① 没有通知渠道（只有 Firing，没人看界面）② 路由错了（发到没人看的群）③ 没有认领机制。
→ 再追"怎么改"：接 Alertmanager + 分级路由 + 值班表 + 升级策略。**这是流程问题，不是技术问题。**

| 没碰过 | 说明 |
|---|---|
