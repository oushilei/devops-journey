# 05 · 故障处置

> 核心一句话：**先止血，后定位。**
> 用户在流血的时候，你在旁边做根因分析，是最典型的处置失误。

---

## 0. 一分钟版本

> 我做过一次完整的故障演练：注入一个"容器能正常跑、但 80 端口不监听"的坏版本，走完真实发布流程。结果是——流水线 `deploy-job` 超时变红，新 Pod 卡在 `0/1`，但**外部访问全程 HTTP 200**，因为 `maxUnavailable: 0` 保住了旧 Pod。同时发现一个更严重的问题：**四个监控 target 全 up、零告警**，故障真实存在却没有任何信号。补了 `PodNotReady` 规则后才触发 `Firing`，最后用 `TARGET_TAG` 按 tag 回滚恢复。

## 一、判定顺序（这一节比任何命令都重要）

### 1.1 三段式

```
① 确认影响面  →  ② 止血  →  ③ 定位根因
   （1 分钟）      （最快手段）    （可以慢）
```

**为什么必须先止血**：

| 顺序 | 后果 |
|---|---|
| 先定位再止血 | 用户持续受影响，而且你在压力下分析容易出错 |
| 先止血再定位 | 服务恢复，你有充裕时间做根因分析，且**故障现场已经保存**（日志、指标） |

> **例外**：如果止血手段会**破坏现场**（比如重启会清掉内存里的状态），要先把关键信息 dump 出来再动手。

### 1.2 第一步：确认影响面（问四个问题）

| 问题 | 怎么查 | 为什么重要 |
|---|---|---|
| **影响谁** | 全部用户 / 部分用户 / 某个功能 | 决定严重级别和要不要惊动人 |
| **什么时候开始** | 看监控曲线拐点、发布记录 | 大概率能找到"变更"这个根因 |
| **是不是刚发布** | `kubectl rollout history`、CI 记录 | 80% 的故障和变更相关 |
| **影响在扩大吗** | 错误率曲线趋势 | 决定是"等"还是"立刻动手" |

**一个关键判断**：

```
如果故障时间点和某次发布/配置变更吻合 → 优先怀疑变更，优先考虑回滚
```

**这条不是猜测，是统计规律**。所以第一件事应该是**查最近有没有变更**，而不是去读代码。

### 1.3 第二步：止血手段的优先级

| 手段 | 速度 | 副作用 | 什么时候用 |
|---|---|---|---|
| **回滚** | 秒~分钟 | 小（回到已知好状态） | 变更是根因时，**首选** |
| 扩容 | 分钟 | 小 | 容量不足、单副本故障 |
| 摘流量（改 selector / 摘 endpoints） | 秒 | 中（功能缺失） | 定位不明、需要先保住核心链路 |
| 重启 | 秒~分钟 | **大（破坏现场）** | 进程卡死且无其他手段 |
| 改配置热加载 | 秒 | 中 | 明确的配置错误 |

**顺序原则：回滚 > 摘流量 > 扩容 > 重启。**

**为什么"重启"排最后**：
- 它**不解决根因**，只是让进程重来一遍
- 它**破坏现场**（内存状态、临时日志没了）
- 它会让"偶发问题"变成"暂时看不见"，下次再来一次

### 1.4 第三步：定位（这时才看日志）

```bash
# 1) 最近有没有变更
kubectl rollout history deploy/<name>
git log --oneline -5

# 2) 对象状态
kubectl get pods -l app=<name> -o wide
kubectl get rs -l app=<name>
kubectl get endpoints <name>

# 3) 事件（最有信息量的地方）
kubectl get events --sort-by=.lastTimestamp | tail -20

# 4) 日志
kubectl logs <pod> --tail=100
kubectl logs <pod> --previous        # 崩溃过的看这个

# 5) 描述（探针失败、调度失败都在这）
kubectl describe pod <pod> | tail -30
```

**`kubectl get events` 是最被低估的一条命令**——它按时间排序，能看到"什么时候发生了什么"，比 `describe` 更全局。

## 二、D2 完整事故时间线（实测）

### 2.1 背景

| 项 | 内容 |
|---|---|
| 目的 | 验证 W4/W5 的防护在**真实发布流程**里是否生效（而不是各自单独实验） |
| 故障设计 | nginx 监听 8080 而不是 80 → **容器正常跑、构建正常过、单测正常过、只有探针能拦** |
| 安全边界 | `maxUnavailable: 0` + readinessProbe → 旧 Pod 撑流量，外部全程 200 |

**为什么选这种故障**（这是设计上的关键）：

> 如果让容器直接崩溃（CrashLoopBackOff），太显眼，验证不到探针的价值。
> **"构建成功、进程活着、服务不可用"才是生产上最阴险的一类故障**——所有自动化检查都会放行。

### 2.2 时间线

| 阶段 | 事件 | 证据 |
|---|---|---|
| 注入 | Dockerfile 加 `COPY nginx-bad.conf`，commit `af006ff` | 部署前单独起容器实测：`Up`、8080 通、80 拒绝 |
| 构建 | pipeline #57：build / test / package 全绿 | **门禁全部放行**（故意不碰 `index.html`） |
| 部署 | `deploy-job` 执行，**90 秒超时 failed** | 日志 `error: timed out waiting for the condition` |
| K8s | 新 Pod `hello-5c9579fc47-k5rcn` **0/1**、`RESTARTS 2`、`Running` | 探针拦住，容器没崩 |
| K8s | 新 RS **REV 24、DESIRED 1、READY 空**；旧 RS **REV 23、DESIRED 2、READY 2** | 新版本没接管 |
| 流量 | endpoints 只有旧 Pod IP（`10.244.1.60/61:80`） | 新 Pod 不在里面 |
| **用户** | **HTTP 200、页面仍是上一版** | **核心结论：用户无感** |
| 监控 | 4 个 target 全 `up`、`Firing` 数 = **0** | **告警缺口暴露** |
| 补规则 | 加 `PodNotReady` → `firing`，`activeAt` 23:25 | 补上后能抓到 |
| 回滚 | `rollback-job` 填 `TARGET_TAG=7d75d679`（通道 B） | 镜像回到好版本 |
| 恢复 | `2/2`、坏 Pod 消失、`Firing` 归零 | 环境干净 |

### 2.3 这次演练暴露的三件事

| # | 发现 | 意义 |
|---|---|---|
| 1 | **流水线红 ≠ 服务挂** | 探针 + `maxUnavailable:0` 把"发布失败"和"服务故障"解耦了 |
| 2 | **能采集 ≠ 能告警** | target 全 up 时故障照样存在，规则只覆盖了采集层 |
| 3 | **回滚通道 B 在真实事故里可用** | 不依赖 RS 历史，只依赖制品还在 |

**第 2 条是整次演练最值钱的产出**：它证明了"监控体系"和"告警覆盖"是两件事。

## 三、判定树（看到现象 → 指向什么）

### 3.1 从"用户说打不开"开始

```
用户报障
  ├── 全站打不开？
  │     ├── NodePort/域名通吗 → 不通 → 查 Service / kube-proxy / 网络插件
  │     └── 通但 5xx → 查 Pod 状态 / 应用日志
  ├── 部分功能异常？
  │     └── 大概率是应用层或依赖（数据库/缓存），不是基础设施
  └── 偶发超时？
        └── 查资源瓶颈（CPU 限流 / 连接数 / 慢查询）
```

### 3.2 从 Pod 状态开始（最常见）

| Pod 状态 | 指向 | 下一步 |
|---|---|---|
| `Pending` | 调度失败 | `describe` 看 Events（资源/污点/亲和性/PVC） |
| `ImagePullBackOff` | 拉镜像失败 | 查 tag 是否存在、registry 认证、网络 |
| `CrashLoopBackOff` | 容器反复退出 | `logs --previous`、退出码、liveness 是否太激进 |
| `Running 0/1` | **进程活着但不 Ready** | `describe` 看探针报错、`endpoints` 是否摘掉 |
| `Running 1/1` 但不通 | 网络或 Service | `endpoints` 有没有 IP、kube-proxy 规则 |
| `Terminating` 卡住 | 有 finalizer 或优雅退出超时 | `describe`、`--force --grace-period=0`（慎用） |

### 3.3 「Pod 全 Running 但访问 000」——三类原因

| 检查 | 结论 |
|---|---|
| `endpoints` 为空 | selector 不匹配 或 Pod 都不 Ready |
| `endpoints` 有 IP，但只有部分节点不通 | **该节点的网络插件异常**（我踩过：flannel vxlan 被 NetworkManager 置 DOWN） |
| `endpoints` 有 IP，所有节点都不通 | Service 端口/targetPort 写错，或 kube-proxy 没跑 |

**判据**：

```bash
ip link show flannel.1        # 看有没有 DOWN
kubectl get pods -n kube-flannel
iptables -t nat -L KUBE-SERVICES -n | grep <ClusterIP>
```

## 四、回滚决策

### 4.1 什么时候回滚

| 条件 | 判断 |
|---|---|
| 故障时间点与最近发布吻合 | **优先回滚** |
| 影响面在扩大 | **立刻回滚**，不要等定位 |
| 已定位到是配置错误且能热修 | 可以热修，但要评估风险 |
| 回滚会丢数据（有 DB migration） | **不能直接回滚**，要先评估兼容性 |

**最后一条是真正的难点**：如果新版本做了不兼容的数据库变更，回滚代码会导致旧代码读不懂新数据。**这是"回滚不是万能"的典型场景。**

### 4.2 用哪条通道

| 场景 | 通道 | 命令 |
|---|---|---|
| 刚发布，历史版本还在 | **A：undo**（快） | `kubectl rollout undo deploy/hello` |
| 历史被清理，或要退到指定版本 | **B：按 tag** | `kubectl set image deploy/hello hello=<image>:<tag>` |
| 完全不知道上一个好版本是哪个 | 先查 CI 记录 / registry tags | `curl .../tags/list` |

**我的实测**：D2 用的是通道 B，因为 `revisionHistoryLimit` 之前被改成 1 又改回来，历史 RS 不完整。**这个细节说明了"知道两条通道各自什么时候失效"的价值。**

### 4.3 回滚后必须做的事

| # | 动作 | 为什么 |
|---|---|---|
| 1 | 验证服务恢复（HTTP 200 + 关键功能） | 回滚也可能失败 |
| 2 | 确认告警恢复 `inactive` | 否则会一直响 |
| 3 | **撤销代码里的坏改动** | 否则下次 push 又是坏镜像（我踩过） |
| 4 | 记录时间线 | 复盘材料 |
| 5 | 补一条告警规则 | "这次为什么没提前发现" |

**第 3 条是真实教训**：回滚只改了集群里的镜像，**代码仓库里还是坏的**。下次任何人 push 都会再产出一个坏镜像。

## 五、复盘怎么写

### 5.1 结构（四段）

| 段 | 内容 | 关键要求 |
|---|---|---|
| **时间线** | 精确到分钟：什么时候发生、什么时候发现、什么时候恢复 | **不写"大约"，写时间戳** |
| **根因** | 直接原因 + 深层原因 | 要能回答"为什么会发生"和"为什么没被挡住" |
| **影响** | 影响了谁、多久、多大范围 | 用数据，不用形容词 |
| **改进项** | 每项要有**负责人和期限** | 没有 owner 的改进项等于没写 |

### 5.2 复盘的三个层次（这决定复盘有没有价值）

| 层次 | 例子 | 价值 |
|---|---|---|
| **表层**：现象 | "Pod 不 Ready" | 低 |
| **中层**：直接原因 | "nginx 监听错端口" | 中 |
| **深层**：为什么没挡住 | "单测只检查文件存在，不检查运行时行为；告警只覆盖采集层" | **高** |

**只写前两层的复盘等于没做**——因为同类问题还会以别的形式再来一次。

### 5.3 我的 D2 复盘示例（改进项部分）

| 改进项 | 类型 | 状态 |
|---|---|---|
| 补 `PodNotReady` 告警规则 | 技术 | ✅ 已做 |
| 单测增加"端口连通性"检查 | 技术 | ❌ 未做（`test.sh` 仍只查文件） |
| 回滚后自动 revert 代码 | 流程 | ❌ 未做（手工执行） |
| 发布后自动对比新旧版本的关键指标 | 技术 | ❌ 未做 |

**诚实说明**：四条里只做了 1 条。**这是实验环境的特点——没有外部压力推动改进项闭环。** 生产环境里，未闭环的改进项会在下次事故时被翻出来问责。

## 六、参考案例（公开资料，非我的经历）

> 下面这个案例是公开可查的真实生产事故，用来对照"生产环境比实验多什么"。
> **我没有参与，只是读过官方事后报告。**

### Cloudflare 2019-07-02 全球故障（27 分钟，丢失约 80% 流量）

| 维度 | 内容 |
|---|---|
| 根因 | WAF 团队部署一条 XSS 检测规则，其中的正则 `.*.*=.*` 会**灾难性回溯**，把全球边缘节点 CPU 打到接近 100% |
| 为什么没挡住 | 官方报告原话：变更流程本身"全都做对了"（PR、审批、CI、变更单都走了），但**测试套件没有识别 CPU 过度消耗的能力** |
| 放大因素 | 配置通过 Quicksilver **p99 2.29 秒**推到 180+ 城市，**没有灰度**——所有节点几乎同时中招 |
| 发现 | 3 分钟后外部拨测触发告警；官方承认"流量骤降的告警触发太慢" |
| 定位难点 | 一开始误判为"遭到攻击"，靠 CPU 数据 + `strace` 才确认是自家规则 |
| 恢复 | 原计划回滚要跑两次完整构建，太慢；改用全局 terminate 快速禁用组件，再按城市灰度恢复 |
| 复盘 | 列出 11 条 what went wrong，改进项包括"WAF 规则改成和其他软件一样的灰度发布流程" |

**这个案例和我的 D2 演练是同一个剧本，只差一层防线**：

| 环节 | 我的 D2 | Cloudflare |
|---|---|---|
| 变更 | 加一行 COPY | 改一条 WAF 规则 |
| CI 门禁 | 全绿（测不到运行时行为） | 全绿（测不到 CPU 回归） |
| 发布范围 | 2 个 Pod 逐个换 | 全球 180+ 城市，无灰度 |
| **发布时拦截** | **探针挡住** | **没有任何拦截** |
| 用户影响 | HTTP 200 全程 | 全球 502，丢 80% 流量 |

> **结论：差别不在"谁的流程更规范"，在"有没有一层在运行时拦住坏东西的机制"。**
> 我的环境里这层是探针；Cloudflare 那种"配置下发"型变更没有实例概念，只能靠**灰度**。

## 七、追问清单

**Q1：线上出故障，你先做什么？**
→ 先确认影响面（谁受影响、什么时候开始、是不是刚发布、在不在扩大），然后**止血**，最后才定位根因。
→ 再追"为什么不先查根因"：用户还在受影响，而且压力下分析容易错。**先回滚保住服务，再慢慢查。**

**Q2：止血手段的优先级？**
→ 回滚 > 摘流量 > 扩容 > 重启。重启排最后，因为它不解决根因且破坏现场。
→ 再追"什么情况必须重启"：进程卡死且无法热修、内存泄漏无法在线恢复。但要先 dump 现场。

**Q3：怎么判断故障和发布有关？**
→ 看时间点是否吻合。80% 的故障和变更相关，所以第一件事是查最近有没有发布/配置变更。
→ 再追"如果最近没发布呢"：查容量（是否到了瓶颈）、依赖（数据库/缓存/第三方）、流量（是否有突增或攻击）。

**Q4：Pod 一直 0/1，你会重启它吗？**
→ 不会。0/1 说明进程活着但探针不过，删了 RS 会重建，还是 0/1。**根因在镜像或配置**。
→ 再追"那怎么办"：如果是发布导致的，回滚；如果是配置问题，修配置再滚动。

**Q5：回滚有风险吗？**
→ 有。如果新版本做了不兼容的数据库变更，回滚代码会导致旧代码读不懂新数据。另外回滚只改集群，**代码仓库里还是坏的**，下次 push 会重现。
→ 再追"怎么防"：数据库变更要向前兼容（先加字段不删、双写过渡）；回滚后必须 revert 代码。

**Q6：怎么判断"服务恢复了"？**
→ 不能只看 Pod `1/1`。要看：① 外部 HTTP 状态码 ② 关键业务功能 ③ 错误率曲线回到基线 ④ 告警回到 `inactive`。
→ 再追"Pod Ready 不就代表好了吗"：Ready 只说明探针过了，**不代表流量真的通了**（iptables 收敛有延迟），也不代表业务正确。

**Q7：复盘要写什么？**
→ 时间线（精确到分钟）、根因（直接原因 + 为什么没挡住）、影响（数据）、改进项（有 owner 有期限）。
→ 再追"最容易漏的是什么"：**"为什么没被挡住"这一层**。只写"nginx 配错了"没有价值，要写"单测测不到运行时行为、告警只覆盖采集层"。

**Q8：告警响了但没人处理，问题在哪？**
→ 三种可能：没有通知渠道（只有 Firing 没人看界面）、路由错了（发到没人看的群）、没有认领机制。
→ 再追"怎么改"：接 Alertmanager + 分级路由 + 值班表 + 超时升级。**这是流程问题。**

**Q9：你的环境里"救人工具自己挂掉"这种情况有吗？**
→ 我的环境里没有独立故障域——Prometheus、GitLab、Runner 全在 node1 上，node1 挂了监控和 CI 一起没。
→ 再追"生产怎么避免"：监控与被监控对象分故障域、告警通道独立于业务网络、保留一套带外访问方式（如串口/带外管理）。**这块我只理解原理，没实操过。**

**Q10：怎么验证"用户真的没受影响"？**
→ 不能只看自己 curl 一次。要看：① 多个时间点的连续探测 ② 错误率/延迟指标曲线 ③ 如果有真实流量，看业务指标。
→ 再追"我这次怎么验证的"：连续 curl 拿 HTTP 200 + 页面版本号没变 + endpoints 只含旧 Pod + 监控 target 全 up。**四条独立证据。**

## 八、闭卷自测（8 题）

| # | 题 | 及格线 |
|---|---|---|
| 1 | 故障处置的三段式顺序 | 影响面 → 止血 → 定位 |
| 2 | 为什么"重启"排最后 | 不解决根因 + 破坏现场 |
| 3 | Pod `0/1` 时该不该删 Pod | 不该，根因在镜像/配置 |
| 4 | 回滚的两条通道和各自失效条件 | undo 依赖 RS 历史；tag 依赖制品 |
| 5 | 回滚后必须做的三件事 | 验证恢复、撤销坏代码、补告警 |
| 6 | 复盘的三个层次 | 现象 / 直接原因 / 为什么没挡住 |
| 7 | `maxUnavailable: 0` 在故障中的表现 | 发布卡住但服务不中断 |
| 8 | 怎么证明"用户没受影响" | 四条独立证据，不是单次 curl |

## 九、边界

| 没做过 | 说明 |
|---|---|
| **真实生产事故处置** | 只有演练。**不能说"处理过生产事故"** |
| 值班 / on-call | 没有值班经验、没有 SLA 压力 |
| 跨团队协作处置 | 单人在自己环境操作 |
| 数据库回滚 / 数据修复 | 只回滚过无状态应用 |
| 故障演练的混沌工程工具 | 手工注入，没用 Chaos Mesh 之类 |
| 大规模故障（多集群/多地域） | 单集群 |

> **对外表述的准确说法**：
> "我在实验环境完整演练过一次故障闭环：注入坏版本、验证探针拦截、发现告警缺口、补规则、按 tag 回滚。"
> **不能说**："我处理过线上故障"。
