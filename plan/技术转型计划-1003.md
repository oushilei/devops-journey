### ✅ Day 2（10/3 周六）—— docker-compose【已完成】

**目标**：用一条命令同时起应用和 nginx 反向代理

**为什么做**：真实项目从来不是一个容器。compose 是"多容器编排"的入门，
也是面试高频题（"你怎么管理多个容器？"）。

**任务**：

1. 在 `~/devops-demo/` 下新建 `nginx.conf`：

```nginx
server {
    listen 80;
    location / {
        proxy_pass http://app:8080;
    }
}
```

2. 新建 `docker-compose.yml`：

```yaml
services:
  app:
    build: .
    image: devops-demo:slim
    expose:
      - "8080"

  nginx:
    image: nginx:alpine
    ports:
      - "8081:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app
```

> 用 8081 而不是 80，是因为 k8s-node1 上已经有别的 nginx 容器，
> 80 端口很可能被占。用 8081 可以避开冲突。

> **⚠️ 已知坑（10/3 实测）**：`nginx:alpine`（1.31.6）在 CentOS 7 的 3.10 内核上**无法启动**，
> 报错 `[crit] "/run/nginx.pid" failed (1: Operation not permitted)`。
> 已用隔离实验确认：**与 compose 配置无关，是镜像与老内核的兼容问题**。
> **解法：把镜像换成 `nginx:1.24-alpine`**；若仍不行，在服务下加 `tmpfs: ["/run"]`。

3. 先确认 compose 可用：`docker compose version`
   （如果报 "not a docker command"，说明没装 compose 插件，先告诉我）
4. 先停掉之前手动跑的容器：`docker rm -f demo-slim`
5. 启动：`docker compose up -d`
6. 验证：`docker compose ps`、`curl localhost:8081`

**你要自己搞懂的 4 个问题**（想不出来再问我）：
- `expose` 和 `ports` 有什么区别？
- nginx 配置里为什么能直接写 `app:8080` 而不是 IP？
- `depends_on` 能保证 app 已经启动完成吗？
- `:ro` 是什么意思？

**验收**：贴 `docker compose ps` 和 `curl localhost:80` 的输出
**预计耗时**：2 小时

### ✅ Day 3（10/3 周六）—— Docker 网络（已压缩，只做网络）【已完成】

> **调整说明（10/3）**：原计划的**数据卷部分砍掉**。理由：数据卷在 K8s 里对应 PV/PVC，
> 是另一套模型，现在学性价比低；而**网络部分直接服务于 K8s 的 CNI / Service / Pod 网络**，
> 必须保留。省下的时间全部给 Week 4 的 K8s。

**目标**：搞懂容器之间怎么通信 —— 这是理解 K8s 网络的前置

**任务**：

1. 先看 compose 帮你建的网络：
   ```bash
   docker network ls
   docker network inspect devops-demo_default
   ```
2. **对照实验 A**：在默认 bridge 网络里跑两个容器，用名字 ping
   ```bash
   docker run -d --name b1 alpine sleep 3600
   docker run -d --name b2 alpine sleep 3600
   docker exec b1 ping -c 2 b2
   ```
3. **对照实验 B**：在自定义网络里做同样的事
   ```bash
   docker network create mynet
   docker run -d --name c1 --network mynet alpine sleep 3600
   docker run -d --name c2 --network mynet alpine sleep 3600
   docker exec c1 ping -c 2 c2
   ```
4. 清理：`docker rm -f b1 b2 c1 c2`

**你要自己搞懂的 2 个问题**：
- 默认 bridge 网络里，容器能用名字互相 ping 通吗？为什么？
- 生产环境为什么推荐自定义网络？

**验收**：贴两次 ping 的结果（一次失败、一次成功）
**预计耗时**：1 小时

### ✅ Day 4（10/3 周六）—— 把镜像推进仓库【已完成】

**目标**：走通"构建 → 打标签 → 推送 → 拉取"完整链路

**为什么做**：这就是 CI/CD 里"推镜像"那一步。**Jenkins 和 GitLab CI 都会做这件事，
你先手工走一遍，后面自动化时才知道它在干什么。**

**任务**：

1. 起一个本地仓库：
   ```bash
   docker run -d -p 5000:5000 --name registry registry:2
   ```
2. 给镜像打标签（指向仓库地址）：
   ```bash
   docker tag devops-demo:slim localhost:5000/devops-demo:v1
   ```
3. 推送：`docker push localhost:5000/devops-demo:v1`
4. 删掉本地两个标签：`docker rmi devops-demo:slim localhost:5000/devops-demo:v1`
5. 从仓库拉回来：`docker pull localhost:5000/devops-demo:v1`
6. 查看仓库里有什么：`curl localhost:5000/v2/_catalog`

**你要自己搞懂的 3 个问题**：
- 为什么推之前必须先 `docker tag`？
- 仓库地址前缀的作用是什么？
- 如果推送时报 `http: server gave HTTP response to HTTPS client`，原因是什么？

**验收**：贴 push、pull、`_catalog` 三处输出
**预计耗时**：1.5 小时
