## 二、W6 的核心结论（三条）

### 1. 六段链路第一次真正连通

```
Git 交付代码 → CI 自动验收并产出不可变制品 → 人工点一次发布
→ K8s 声明式换 Pod → 三个 exporter 记录变化 → 查询验证
```

**只有第 1 步和第 4 步需要人**，其余全靠机器。实测时间戳：

| 时间（UTC） | 事件 |
|---|---|
| `13:27:48Z` | 新 RS `hello-8c74fb44`（REV 23）创建 |
| `13:27:49Z / 13:27:59Z` | 两个新 Pod 启动 |
| `21:28 / 21:30`（北京时间） | 监控侧新序列首点出现 |

两套独立数据对得上，延迟约 1~2 分钟 = `scrape_interval 15s` + cAdvisor 就绪延迟。

### 2. 「流水线红 ≠ 服务挂」，探针 + maxUnavailable:0 能兜住

故障演练实测：

| 层 | 现象 |
|---|---|
| 流水线 | `deploy-job` 超时变红，REV 24 未完成 |
| K8s | 新 Pod `0/1` `CrashLoopBackOff`，旧 RS 保持 2/2 |
| 用户 | **`HTTP 200` 全程不变**，页面仍是上一版 |

### 3. 「能采集 ≠ 能告警」——这是 W6 最有价值的发现

故障期间四个 target **全 up**、`Firing` 数 **0**。因为原有规则只有 `up == 0`。

补上 `PodNotReady` 后才真正触发：

```yaml
- alert: PodNotReady
  expr: kube_pod_status_ready{condition="false",namespace="default"} == 1
  for: 1m
  labels: {severity: critical}
```

**机制澄清**：Prometheus 不"决定看谁"，它拉的是 kube-state-metrics 暴露的**控制面全量对象清单**。
endpoints 只挂 Ready 的 Pod（数据面），不影响不 Ready 的 Pod 被记录（控制面）。两套系统互不干扰。

## 三、W6 踩坑清单（6 条）

1. **`localhost:9090` 只在 node1 有效**：master 上查会静默无输出（`curl -s` 吞掉错误），跨机要写 `192.168.245.150:9090`。
2. **`curl` 原始 JSON 人眼读不了**：`query_range` 必须格式化（`tr` + `grep -o` + `awk` + `date -d @`）；用 `container="hello"` 而非 `!="POD"` 避免重复序列。
3. **`git status` 的 `ahead N` 不可信**：之前用带凭据完整 URL 推送，本地 `origin/main` 指针陈旧；用 `git ls-remote` 确认真实 HEAD。
4. **`revisionHistoryLimit: 10` 是上限不是配额**：W4 改 limit=1 时旧 RS 被真删除，改回不复活；当前 RS 不占额度。REV 已到 23 但对象只剩 3 个。
5. **`for: 1m` 从规则加载时重新计时**：reload 后 `sleep 20` 只能看到 `pending`，不是 `firing`。
6. **`grep -o '"labels":{[^}]*}'` 匹配不上**：`{` 在基础正则里是区间起始，导致"验证无输出"的误判。改用 `tr ',' '\n' | grep -E`。
